## 현재 작업 기준

우선 사용자는 **공공기관의 내부 관리자·수질 분석·도로 조사 담당자**입니다. 하지만
Core의 출발점은 KRDS가 아니라 **K-AQUAS와 D-ROAD의 제품 코드**입니다. 기존 기준색,
제공 로고, 메뉴 구조와 익숙한 흐름을 유지하면서 접근성·불일치·임시방편을 고칩니다.
판단 순서는 **제품 근거 → Core 공통화 가치 → KRDS·접근성 점검**입니다. KRDS는 필요한
일부 원칙만 선택해 참고하며 전체 항목을 구현 목표로 삼지 않습니다. KRDS 채택 범위와
예외는 [`docs/PUBLIC_SECTOR_DIRECTION.md`](docs/PUBLIC_SECTOR_DIRECTION.md)에서만 정의합니다.

대표 화면 제외 Core 디자인과 D-FIND 제품 표현을 관리합니다.
[React 내부 패키지](packages/react/README.md) v0.3.3은 HTML 견본과 공통 요소의
상태·사용 범위를 맞췄지만 **실제 서비스 적용은
아직 없습니다.** 다른 코드 에이전트가 이어받을 때는 `README.md`와
[`docs/HANDOFF.md`](docs/HANDOFF.md)를 먼저 읽고, 완료한 변경·다음 작업·검증 결과를
그 문서와 [`docs/STATUS.md`](docs/STATUS.md)에 갱신합니다. 아이콘 출처는 [공통 시각 스타일](docs/VISUAL_STYLE.md#아이콘-출처와-사용-기준)을 따른다.
기존 디자인 시스템 파일을
수정하기 전에는 사용자에게 목적·파일·영향·되돌리는 방법을 알립니다.

2026-10-01 승인된 D-ROAD 구조를 [세 제품 인증 시안](components/auth.html)으로 확장했습니다.
제품별 로그인·가입 React 조합도 v0.3.0에 포함했고 [폼 기준](docs/FORM_LAYOUT.md#인증-화면--d-road-대표-시안)을 따릅니다.

같은 날 승인된 통합 플랫폼 방향을 [앱 셸 HTML 검토안](components/navigation.html)으로 구현했습니다.
공통 헤더 아래에 제품별 지도·관리 탐색을 유지합니다. K-AQUAS는 기존 업무 메뉴 전체와
관리 3종의 가상 작업 배치까지 확장했으며, [범위와 시연 경계](docs/VISUAL_STYLE.md#k-aquas-전체-메뉴-검토안)를
따릅니다. 홈은 기존 K-AQUAS MainPage를 사용하고 사이드메뉴는 제품 원본 아이콘을 유지합니다.
최신 소유자 결정에 따라 **K-AQUAS 카테고리별 내부 배치·작업 흐름은 기존 그대로,
표현은 Core 스타일로 교체**했습니다. 10/2 후속 요청으로 K-AQUAS 헤더를 낮추고
유역 드롭다운을 제거했으며 이동·초기화 도구를 캡처 아래 세로로 분리했습니다.
후속 요청으로 패널의 회색 면·중복 구분선을 줄이고 D-FIND의 150/200ms 전환을
K-AQUAS 시안에 시험 적용했습니다.
소유자가 현재 헤더·메뉴·지도 도구·모션 규칙을 승인했습니다. 영주댐·레이어 목록 카드는
비워진 도구 공간만큼 왼쪽으로 옮겼습니다. [시각 규칙](docs/VISUAL_STYLE.md#2026-10-02-k-aquas-지도-공간-후속-검토)의
기준을 D-ROAD·D-FIND HTML 셸에도 반영했습니다. 프로젝트 계층·지도 위 패널·보고서 전환 등
기존 업무 배치는 유지합니다. [제품별 확장 기준](docs/VISUAL_STYLE.md#2026-10-02-d-road와-d-find-셸-공통-스타일)을
따르며 새 패널 시안 검토 후 React 셸을 만듭니다.

최신 공통화 요청에 따라 세 제품 메뉴는 **72px 고정 레일·아이콘+텍스트**로 맞췄습니다.
이미 구현한 Core 요소는 재설계하지 않고 관리 아이콘·메뉴 상태·패널 제어의 남은 차이만
반영했습니다. [현재 공통 메뉴 기준](docs/VISUAL_STYLE.md#2026-10-02-공통-메뉴와-패널-확정)이
이전 아이콘 전용/플로팅 시안보다 우선합니다.

2026-10-06 [K-AQUAS 업무 컴포넌트](components/k-aquas-business.html)에 실제 제품의
다중 업로드·분석인자·분석 상세·차트/범례·처리 현황 디자인을 보강했습니다.
기존 셸에도 같은 원본을 연결했으며 [제품 조합 기준](docs/VISUAL_STYLE.md#2026-10-06-k-aquas-업무-컴포넌트)을 따릅니다.

## 견본에서 쓰기

CSS 세 개를 순서대로 넣고, 상위 요소에 브랜드·명도·밀도를 지정합니다.

```html
<link rel="stylesheet" href="fonts.css">
<link rel="stylesheet" href="tokens.css">
<link rel="stylesheet" href="components/base.css">

<body data-brand="k-aquas" data-scheme="light" data-density="default">
  <button class="btn btn--md btn--primary">저장</button>
</body>
```

같은 마크업이 `data-brand="d-road" data-scheme="dark"`에서 D-ROAD 색으로 렌더됩니다.
`data-brand="d-find" data-scheme="dark"`에서는 D-FIND의 녹색·다크 표면과
기존 흰색 primary 버튼으로
렌더됩니다. [D-FIND 제품 표현](components/d-find.html)에서 작은 Core 요소를 확인합니다.
기존 견본의 `data-product="k-aquas"`와 `data-product="d-road"`도 호환 프리셋으로
계속 작동합니다. `compact`는 좁은 표·지도 패널에만 씁니다.
직접 CSS를 연결하는 예시입니다. React에서는 [내부 패키지](packages/react/README.md)의
`ThemeScope`와 컴포넌트를 사용합니다. 기존 MUI·Tailwind 화면에는
[제품별 적용 매핑](docs/APPLICATION.md#제품별-유지변경-매핑--적용-전-기준)을 따라 연결합니다.

**색을 직접 쓰지 마세요.** 하드코딩 hex 대신 역할 토큰을 씁니다.

```css
background: var(--dm-primary-solid);   /* O */
background: #5098EC;                   /* X — 제품이 바뀌면 안 따라옴 */
background: var(--dm-accent-500);      /* X — 색상 단계 직접 참조. K-AQUAS는 500, D-ROAD는 400이 기준 */
```

## 고치기

순서가 있습니다. **`tokens/source.json` → `npm run tokens:build` → `components/base.css` → 견본 페이지.**
견본에서 먼저 고치면 컴포넌트 CSS와 갈라집니다 — 그 갈라짐을 정리하려고 만든 시스템입니다.

`tokens.css`는 생성 파일이므로 직접 수정하지 않습니다. 변경 뒤에는 다음 검사를 실행합니다.

```bash
npm ci
npm run tokens:build
npm run icons:build
npm run react:build
npm run check
```

이 명령은 JSON과 CSS 동기화, 별칭의 누락과 순환, 토큰 참조, HTML 링크와 라벨,
주요 색 조합의 대비, React 동작·타입과 패키지 CSS 동기화를 확인합니다.

값을 추가하기 전에 두 가지를 확인합니다.

1. **실측 근거가 있는가** — 최신 `context/06-product-audit-2026-09-23.md`와 제품 코드에
   있는 값인가, 아니면 새로 만드는 것인가. `context/01-as-is.md`는 역사적 스냅샷이다.
2. **역할 토큰인가** — 컴포넌트가 색상 단계(`--dm-accent-500`)를 직접 보면 제품을 하나 더 붙일 때 깨집니다

컴포넌트를 추가할 때는 `context/03-rules.md`의 규칙 14개로 판단합니다.
누가 만들어도 같은 결론에 닿게 하는 것이 그 문서의 목적입니다.

## 이 시스템이 존재하는 이유

세 제품(K-AQUAS · D-ROAD · D-FIND)이 **한 회사 제품으로 보이게** 하기 위해서입니다.
공통 구조와 행동 위에 **브랜드 · 명도 · 밀도** 세 축을 조합합니다. 제품 자산은 정해진 자리에
주입하며, 로고 분석은 이번 구축 범위에서 제외합니다.

## 작동 방식

컴포넌트는 하드코딩 색을 쓰지 않고 **역할 토큰**만 참조합니다.

```css
background: var(--dm-primary-solid);
color:      var(--dm-text-on-solid);
```

상위 요소의 `data-brand`와 `data-scheme`을 바꾸면 같은 마크업이 제품 색과 명도에
맞게 렌더됩니다. 기존 `data-product`는 두 제품의 기본 조합을 유지합니다.

```html
<div data-brand="k-aquas" data-scheme="light" data-density="default"> … </div>
<div data-brand="d-road" data-scheme="dark" data-density="default"> … </div>
<div data-brand="d-find" data-scheme="dark" data-density="default"> … </div>
```

[`foundations/comparison.html`](foundations/comparison.html)에서 두 제품의 이전·기본·
compact 표현을 나란히 검토할 수 있습니다.

Source를 `main` / `root`로 두면 됩니다. 루트의 빈 `.nojekyll` 파일이
밑줄로 시작하는 파일이 무시되는 것을 막아줍니다.
