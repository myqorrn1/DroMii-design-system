# KRDS 채택 범위와 예외 목록

> 2026-09-23 사용자 결정. K-AQUAS·D-ROAD에서 DroMii Core를 추출·리팩토링할 때의
> 점검 범위를 정한다. 제품 실측값과 승인 대기 항목은 단계 2·3에서 다시 확인한다.

## 목적과 판단 순서

DroMii Core는 K-AQUAS와 D-ROAD의 **기존 디자인을 추출하고 고쳐서** 만든다.
기준색, 제공된 로고, 메뉴 구조와 익숙한 업무 흐름을 유지한다. 접근성 문제, 불일치,
임시방편, 라이브러리 기본값처럼 근거가 약한 부분을 고친다. 새 컴포넌트는 두 제품의
공통점이거나 Core로 올릴 명확한 가치가 있을 때 제안한다.

1. **제품 코드 근거:** 운영 D-ROAD React 소스와 로컬 K-AQUAS 프런트에서 실제 값·구조·동작을 확인한다.
2. **Core 가치:** 두 제품의 공통 부분인지, 공통화하면 반복 문제를 해결하는지 판단한다.
3. **KRDS·접근성 점검:** 관공서 실무자가 쓰는 화면으로서 문제를 검토한다. KRDS와 다른
   결정은 자동으로 버리지 않고 아래 예외 목록에 근거를 남긴다.

KRDS는 **참고·점검 기준**이다. 이 저장소가 KRDS 공식 구현이나 정부 누리집이라는 뜻이
아니다. 현재 견본은 기관별 계약 기준이나 KWCAG 2.2 준수를 검증해 인증받은 결과물이
아니며, 실제 제품 화면에서 별도로 확인해야 한다. 이 경계에 관한 설명은 이 문서에서만
관리한다.

## 그대로 따를 점검 기준

- KWCAG 2.2 준수를 목표로 포커스, 키보드, 본문 건너뛰기, 대비, 색 이외의 상태 단서,
  대체 텍스트와 화면 확대를 설계·검증한다.
- KRDS의 업무 도구에 해당하는 기본 패턴 7개를 점검한다: **입력폼, 오류, 확인(위험 동작),
  목록 탐색, 필터링·정렬, 첨부파일(업로드), 도움**. 제품 흐름을 먼저 확인한 뒤 대입한다.
- 제품 기준색 값은 유지한다. 색상 단계 간 차이로 필요한 명도 대비를 보장하는 규칙은
  토큰 재구성 단계에서 수치와 검사 방법을 정한다. 현재 토큰을 곧바로 교체하지 않는다.
- 본문 등 읽기용 텍스트는 행간 150% 이상과 확대에 대응하는 상대 단위를 목표로 한다.
  현행 값과의 차이는 단계 3의 KRDS 대조표에서 검토하고 승인 전에는 값을 바꾸지 않는다.

[KRDS 타이포그래피](https://www.krds.go.kr/html/site/style/style_03.html)는 상대 단위
행간과 150% 이상을 안내하고, [디자인 토큰](https://www.krds.go.kr/html/site/style/style_07.html)은
명도 모드를 설명한다. 드로미의 실제 값은 제품 감사와 승인 후 확정한다.

## 방식만 참고할 항목

- 제목·본문의 단계와 굵기 구조를 참고한다. 본문 크기와 `default / compact` 밀도 축은
  단계 3에서 선택지를 제시하고 소유자 승인을 받는다.
- 선명한 화면 모드는 이번에 만들지 않는다. `brand / scheme / density` 축을 설계할 때
  고대비 명도 모드가 들어갈 자리만 둔다.
- 컴포넌트 문서는 **구조 / 사용 기준 / 접근성 / 상호작용**의 같은 틀로 작성한다.

| D-ROAD 다크 기본값·고대비 | 선명한 화면 모드 등 명도 기준 | **결정 보류** | 기존 D-ROAD 다크 인상을 유지할지 실측·대조 후 단계 3에서 승인받는다. 고대비는 자리만 설계한다. |

예외는 제품 감사 후 단계 3의 `docs/MIGRATION_MAP.md`에 기존 요소와 Core의 연결을
기록하고, `docs/KRDS_ALIGNMENT.md`에 제품·Core·KRDS 실측값을 나란히 놓은 뒤 갱신한다.
