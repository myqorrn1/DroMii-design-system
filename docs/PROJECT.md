# 드로미 디자인시스템 프로젝트 기준

> 기준일: 2026-09-10  
> 최종 승인자: 프로젝트 소유자

## 목적

K-AQUAS, D-ROAD, D-FIND를 포함한 드로미 솔루션에 공용 디자인을 적용한다.
사용자가 어느 솔루션을 사용하더라도 드로미가 만든 제품임을 알아볼 수 있어야 한다.

공통성은 같은 색을 반복하는 방식보다 타이포그래피, 간격, 컴포넌트 구조,
상태 표현, 상호작용, 문구와 품질 기준에서 만든다. 제품의 업무 맥락은 유지한다.

## 완료 범위

- 공용 디자인 토큰과 제품별 테마
- 데스크톱 웹용 실제 CSS와 React 컴포넌트
- 실제 컴포넌트를 직접 보여주는 사내 HTML 문서 사이트
- 컴포넌트 사용 기준, 상태, 접근성, 예시 문구
- 토큰 참조, 접근성, 상호작용, 시각 회귀 자동 검사
- 신규 화면 도입 방법과 기존 화면의 점진적 전환 가이드

## 적용 원칙

1. 데스크톱 웹을 우선한다.
2. 신규 화면부터 적용하고 기존 화면은 점진적으로 전환한다.
3. 기존 기준색은 유지하되 대비와 일관성을 위해 조합과 사용 위치를 바꿀 수 있다.
4. 접근성과 일관성 문제가 있으면 기존 디자인을 변경할 수 있다.
5. 제품 코드에서 확인한 사실과 새로 내린 결정을 구분해 기록한다.
6. 제품별 차이는 실제 업무와 사용 환경의 근거가 있을 때만 둔다.
7. 로고 디자인과 로고 체계 분석은 이 프로젝트 범위에서 제외한다.

## 관리 원칙

- Figma는 필수 관리 도구로 두지 않는다.
- Storybook 도입을 전제로 하지 않는다.
- 토큰 원본, 실제 컴포넌트, 사용 문서를 Git에서 함께 관리한다.
- 사내 문서 사이트는 실제 배포 컴포넌트를 렌더링한다.
- 토큰 표, 컴포넌트 상태와 메뉴처럼 반복되는 정보는 원본에서 자동 생성한다.
- 기존 GitHub 디자인시스템을 수정하기 전에 대상과 영향을 프로젝트 소유자에게 알린다.

## 품질 기준

- WCAG 2.2 AA를 기본 접근성 기준으로 삼는다.
- 마우스 없이 주요 작업을 수행할 수 있어야 한다.
- 상태를 색만으로 전달하지 않는다.
- 일반 텍스트와 플레이스홀더는 최소 대비를 충족한다.
- 컴포넌트의 이름, 속성, 상태와 문서 표현이 일치해야 한다.
- 정의되지 않은 토큰 참조와 문서 수치 불일치를 자동 검사한다.
- K-AQUAS, D-ROAD, D-FIND의 실제 화면에서 검증한 뒤 공용 기준으로 확정한다.

## 권한과 변경 절차

조사, 설계, 구현, 테스트, 커밋, PR, main 병합과 문서 사이트 배포까지 위임됐다.
다만 기존 디자인시스템 파일을 수정하기 전에 다음을 먼저 알린다.

- 수정 목적
- 대상 파일
- 핵심 변경 내용
- 배포 화면과 기존 제품에 미치는 영향
- 되돌리는 방법

## 추가 입력이 필요한 시점

- K-AQUAS와 D-ROAD를 다시 감사할 때: 서버 코드 접근 방법
- D-FIND 테마와 컴포넌트를 정할 때: 프론트엔드 코드 위치
- 실제 화면을 검증할 때: 운영 또는 스테이징 주소와 테스트 계정

이 입력이 없어도 저장소 기준 정비, 토큰 구조 설계, 문서 관리 구조와 공용
컴포넌트 기반 작업은 진행할 수 있다.
