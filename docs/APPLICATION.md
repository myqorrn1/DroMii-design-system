# 제품 적용 전략 — 현재는 문서만

K-AQUAS, D-ROAD, 이후 D-FIND로 DroMii Core를 적용할 때의 순서다. **이번 구축 단계에서는
제품 코드를 수정하지 않는다.** Core 값과 구성 요소는 제품 감사, 마이그레이션 매핑,
소유자 승인을 거쳐 확정한다.

## 적용 전 조건

1. [`현재 상태`](STATUS.md)의 디자인 완료 조건과 승인 지점을 확인한다.
2. `docs/MIGRATION_MAP.md`에 해당 화면의 기존 값·컴포넌트와 Core 대상, 유지·변경·폐기
   이유가 기록돼 있어야 한다. 이 문서는 단계 3에서 작성한다.
3. 기존 화면의 DOM·스타일·상호작용, 제품별 MUI 버전, 빌드·테스트 방법을 기록한다.
4. 운영 또는 스테이징 주소와 테스트 계정은 실제 적용 검증 시 받는다.

## 1. 모습을 바꾸지 않는 토큰 연결

기존 하드코딩 값을 **현재 화면과 같은 값**의 역할 토큰으로 먼저 연결한다. 첫 연결의
완료 조건은 전후 화면과 상호작용이 같다는 것이다. 이때 기준색, 로고, 메뉴 순서와
업무 흐름을 임의로 바꾸지 않는다. 이후 승인된 토큰 값을 바꾸면 기존 화면과 새 화면이
함께 변경될 수 있도록 연결 지점을 기록한다.

```text
기존 값·스타일 → 제품별 호환 토큰(동일 값) → 승인된 Core 역할 토큰
```

`tokens/source.json`은 Core 원본이고 `tokens.css`는 생성 파일이다. 실제 제품에서는
기존 CSS와의 우선순위 충돌을 작은 화면 단위로 해결한다. 호환 CSS에는 대상 화면과
제거 조건을 남긴다.

## 2. MUI 테마 연결 설계

두 제품이 쓰는 MUI 버전은 K-AQUAS v5, D-ROAD v7로
[제품 소스 재감사](../context/06-product-audit-2026-09-23.md)에서 확인했다. K-AQUAS에는
포털 겹침을 막는 z-index 전용 테마가 이미 있다. Core 토큰에서 각 버전에 맞는 MUI 테마를 생성하는
방안을 설계한다. `palette`, `typography`, `shape`, `spacing`, 컴포넌트 기본 상태와
포커스의 연결을 검토하되, MUI 기본값을 제품의 실측 디자인으로 오인하지 않는다.

토큰·테마 연동이 안정화되기 전에는 기존 MUI 사용처를 한 번에 새 컴포넌트로 교체하지
않는다. Core 컴포넌트가 필요한 곳과 MUI 테마만 맞추면 되는 곳은 매핑표에서 구분한다.

## 3. 화면 적용 순서

1. 앱 셸: 헤더·메뉴의 기존 정보 구조와 익숙한 이동 흐름을 유지하며 공통 상태만 연결
2. 버튼·입력·알림: 라벨, 오류, 비활성, 포커스, 처리 중·완료 상태를 정리
3. 표·폼: 검색, 선택, 페이지 이동, 저장과 오류 복구를 실제 API에 맞춰 연결
4. 도메인 화면: 지도·수질 분석·도로 조사 영역은 가장 늦게, 가장 적게 변경

신규 화면부터 적용하고 기존 화면은 수정 빈도와 영향이 낮은 곳부터 점진적으로
전환한다. `MIGRATION_MAP.md`의 유지·변경 경계를 벗어나면 구현하지 않고 제안한다.

## 제품별 확장과 검증

Core로 설명되지 않는 수질 지표·도로 탐지 범례·지도 도구는 제품 확장으로 둔다. 제품
확장도 Core의 대비, 포커스, 오류와 상태 표현을 따른다. 전후 비교에서는 정상 화면뿐
아니라 로딩·빈 상태·서버 오류·권한 제한·긴 이름·많은 데이터·키보드·확대를 확인한다.

적용 PR에는 Core 버전, 교체한 기존 요소, MUI 테마 변경, 제품 확장과 예외, 시각·동작
검증 결과, 되돌리는 방법과 남은 전환 범위를 적는다.
