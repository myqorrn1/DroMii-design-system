# 제품 적용 전략 — 현재는 문서만

K-AQUAS, D-ROAD, 이후 D-FIND로 DroMii Core를 적용할 때의 순서다. **이번 구축 단계에서는
제품 코드를 수정하지 않는다.** Core 값과 구성 요소는 제품 감사와 파운데이션 결정 승인,
이후 제품별 적용 매핑을 거쳐 연결한다.

React에서 공용 UI를 재사용할 때는 [내부 패키지](../packages/react/README.md)를 쓴다.
이 패키지는 Core CSS를 그대로 묶은 독립 요소이며, 기존 MUI·Tailwind 화면을 한 번에
교체하거나 앱 셸을 확정하지 않는다.

## 적용 전 조건

1. [`현재 상태`](STATUS.md)의 디자인 완료 조건과 승인 지점을 확인한다.
2. 아래 제품별 매핑을 해당 화면의 출발점으로 쓰고, 실제 적용 시 현재 브랜치의
   값·DOM·상호작용과 다시 대조한다. 차이가 있으면 매핑을 먼저 고친다.
3. 기존 화면의 DOM·스타일·상호작용, 제품별 MUI 버전, 빌드·테스트 방법을 기록한다.
4. 운영 또는 스테이징 주소와 테스트 계정은 실제 적용 검증 시 받는다.

## 1. 모습을 바꾸지 않는 토큰 연결

기존 하드코딩 값을 **현재 화면과 같은 값**의 역할 토큰으로 먼저 연결한다. 첫 연결의
완료 조건은 전후 화면과 상호작용이 같다는 것이다. 이때 기준색, 로고, 메뉴 순서와
업무 흐름을 임의로 바꾸지 않는다. 이후 승인된 토큰 값을 바꾸면 기존 화면과 새 화면이
함께 변경될 수 있도록 연결 지점을 기록한다.

```text
기존 값·스타일 → 제품별 호환 토큰(동일 값) → 승인된 Core 역할 토큰
```

`tokens/source.json`은 Core 원본이고 `tokens.css`는 생성 파일이다. 실제 제품에서는
기존 CSS와의 우선순위 충돌을 작은 화면 단위로 해결한다. 호환 CSS에는 대상 화면과
제거 조건을 남긴다.

## 2. MUI 테마 연결 설계

두 제품이 쓰는 MUI 버전은 K-AQUAS v5, D-ROAD v7로
[제품 소스 재감사](../context/06-product-audit-2026-09-23.md)에서 확인했다. K-AQUAS에는
포털 겹침을 막는 z-index 전용 테마가 이미 있다. Core 토큰에서 각 버전에 맞는 MUI 테마를 생성하는
방안을 설계한다. `palette`, `typography`, `shape`, `spacing`, 컴포넌트 기본 상태와
포커스의 연결을 검토하되, MUI 기본값을 제품의 실측 디자인으로 오인하지 않는다.

토큰·테마 연동이 안정화되기 전에는 기존 MUI 사용처를 한 번에 새 컴포넌트로 교체하지
않는다. Core 컴포넌트가 필요한 곳과 MUI 테마만 맞추면 되는 곳은 적용 시 매핑에서 구분한다.

D-FIND의 제공 프론트 소스는 MUI 대신 Tailwind와 CSS 변수를 쓴다. 적용 시에는 같은
Core 역할 토큰에서 D-FIND용 CSS 변수·Tailwind 연결을 별도로 설계한다. 세 제품에
MUI 테마 하나를 공통 연결 방식으로 강제하지 않는다. 근거는
[D-FIND 정적 소스 확인](../context/06-product-audit-2026-09-23.md#2026-09-29-d-find-제공-프론트-소스의-셸-확인--정적-읽기-전용)에 둔다.

## 인증 조합 적용 준비

인증 디자인은 `@dromii/react` v0.3.0의 공통 카드·폼으로 정리했다. 아직 제품에 적용하지
않았다. 세 제품의 [실제 React 사용 예시](../packages/react/examples/AuthUsage.tsx)와
[입출력 계약](../packages/react/README.md#인증-화면-사용)을 기준으로 다음만 연결한다.

1. 제품 로고·라우트·정책 문서와 승인된 비밀번호/기억 옵션을 주입한다.
2. 기존 로그인·가입 API 응답을 `onSubmit`과 필드 오류로 변환한다. K-AQUAS는 서버의
   회사 목록을 공급하고, D-ROAD는 중복 확인·발송·인증 응답을 `verification`으로 연결한다.
3. D-FIND는 Google 제공자 함수·버튼 자산을 연결한다. 이메일 가입이나 통합 계정을 신설하지 않는다.
4. 제품에서 실제 성공/실패·중복 요청·만료·재발송·이메일 변경·권한·정책 문서 열기와
   키보드·확대·스크린리더를 검증한다. Core의 인증 완료 표시는 서버 검증을 대신하지 않는다.

API 주소·세션 저장·SSO·인증 정책은 디자인시스템에서 구현하지 않는다. 인증 API와 저장
필드 구조를 바꾸는 결정은 제품 담당자와 별도로 확정한다.

## 3. 화면 적용 순서

1. 앱 셸: 헤더·메뉴의 기존 정보 구조와 익숙한 이동 흐름을 유지하며 공통 상태만 연결
2. 버튼·입력·알림: 라벨, 오류, 비활성, 포커스, 처리 중·완료 상태를 정리
3. 표·폼: 검색, 선택, 페이지 이동, 저장과 오류 복구를 실제 API에 맞춰 연결
4. 도메인 화면: 지도·수질 분석·도로 조사 영역은 가장 늦게, 가장 적게 변경

신규 화면부터 적용하고 기존 화면은 수정 빈도와 영향이 낮은 곳부터 점진적으로
전환한다. 적용 시 기록한 유지·변경 경계를 벗어나면 구현하지 않고 제안한다.

## 제품별 확장과 검증
