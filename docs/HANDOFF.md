## 목표와 판단 순서

K-AQUAS와 D-ROAD의 기존 디자인을 **추출·리팩토링**해 여러 드로미 솔루션이 공유할
DroMii Core를 만든다. 제품의 기준색·제공 로고·메뉴 구조·익숙한 업무 흐름은 보존하고,
접근성·불일치·임시방편·라이브러리 기본값을 고친다.

1. 제품 코드에 근거가 있는가?
2. 두 제품에 공통인가, 또는 Core로 올릴 가치가 있는가?
3. 접근성에 문제가 없는가? KRDS에서 선택한 기준으로 점검할 항목인가?

KRDS 전체를 구현 목표로 삼지 않는다. 채택 범위·예외·표현의 경계는
[한 문서](PUBLIC_SECTOR_DIRECTION.md)에서 관리한다. 제품 코드는 읽기만 한다.

## 현재 결과와 원본

- [현재 상태](STATUS.md)는 완료·미검증의 단일 현황표다. [컴포넌트 목록](COMPONENTS.md)은
  Core 구현·조건부·제품 확장의 경계를 정한다.
- [제품 소스 감사](../context/06-product-audit-2026-09-23.md)는 운영 D-ROAD
  `/home/dromii/dromii_v5_react/src`와 로컬 K-AQUAS `src`를 읽기 전용으로 확인한
  근거다. 과거 Vite 후보를 운영 D-ROAD의 근거로 쓰지 않는다.
- 소유자가 승인한 큰 파운데이션 결정: 본문 default 16px, 표·지도 패널 compact 14px,
  D-ROAD 다크 기본, 고대비 축 예약, 일반 문자 제어 40/44px과 제한된 compact 32px.
  24px은 아이콘 전용이다. 기준색 값과 제공 로고는 유지한다.
- 토큰 원본은 `tokens/source.json`, 생성물은 `tokens.css`, 공용 CSS는
  `components/base.css`다. HTML은 `foundations/`와 `components/`에서 직접 본다.
  제품별 기본 표현과 실제 상태·긴 문구·좁은 폭이 함께 드러나야 한다.
- `docs/FORM_LAYOUT.md`, `DATA_TABLE.md`, `LIST_FILTER.md`, `PATTERNS.md`는 조합
  규칙이다. 제품 적용 순서와 MUI 테마 계획은 [적용 가이드](APPLICATION.md)를 따른다.

## 현재 디자인 경계

파운데이션과 공용 컴포넌트의 CSS·견본·사용 규칙은 v0.18에서 구현했다. 특히
보조 글자·다크 위험색 대비, 긴 라벨·읽기 전용·오류·혼합 선택, 표 정렬·고정 머리글,
경로·드롭다운·펼침, 로딩·조건부 수치 진행률, 범주·숫자가 보이는 차트를 보강했다.
브라우저에서 K-AQUAS 라이트·D-ROAD 다크와 320px·512px 유효 폭 일부를 확인했다.
캐시 때문에 이전 CSS가 남던 문제를 버전이 있는 CSS 링크로 해결했다. 공개 Pages에서
320px 유효 폭의 드롭다운 표시·키보드 선택·Esc 복귀, 긴 버튼 높이, 두 제품의 읽기
전용 입력을 최신 CSS로 확인했다.

2026-09-29 소유자 피드백: 지도가 두 제품의 주 콘텐츠이므로 현재 앱 셸 견본의
고정 248px 사이드 메뉴와 안쪽 24px 콘텐츠 여백을 지도 업무의 최종안으로 보지 않는다.
K-AQUAS 관리자 셸과 지도 도구, D-ROAD의 헤더·메뉴바·프로젝트 목록 차이를 보존하며
공통 구조를 다시 제안해야 한다. 파운데이션 전후 비교의 2열 예시 표가 실제 표의
700px 최소 폭을 상속해 옆 카드를 가리던 문제는 비교 견본에서만 폭을 재정의했다.
로컬 319px·1280px 유효 폭에서 여섯 카드의 입력·표와 페이지 가로 넘침을 확인했다.

**소유자 검토 전 구현안:** [두 운영 셸과 핵심 업무 관찰](../context/06-product-audit-2026-09-23.md#2026-09-29-핵심-업무-화면-후속-확인--읽기-전용)을
반영해 `components/navigation.html`에 지도형·관리형 셸을 분리했다. 지도형은 작업
패널·지도 캔버스·지도 위 제어를 공유한다. K-AQUAS의 기능 레일·지도 위 맥락 카드와
D-ROAD의 상단 바·지도 아래 결과 줄은 제품별 구성을 유지한다. 펼친 패널은 각각
280px·320px 검토값이고 접으면 목록을 아이콘으로 축약하지 않고 지도를 넓힌다.
좁은 유효 폭에서는 패널이 지도 위에 겹쳐져 지도의 최소 공간을 보존한다. 관리형은
별도 변형이며 실제 제품 메뉴 항목을 각각 주입한다. 메뉴·헤더의 공용 시각 규칙은
[시각 스타일](VISUAL_STYLE.md), 구현 경계는 [컴포넌트 목록](COMPONENTS.md)을 따른다.
기존 56px·248px 관리형 치수와 새 지도형 치수는 **소유자 검토 전**이다.

소유자가 제공한 [D-FIND 프론트 소스의 정적 확인](../context/06-product-audit-2026-09-23.md#2026-09-29-d-find-제공-프론트-소스의-셸-확인--정적-읽기-전용)에서
상단 제품·프로젝트 맥락, 지도 위 기능 레일·접는 패널, 같은 공간의 보고서 전환,
별도 관리 화면을 확인했다. D-FIND는 MUI가 아닌 Tailwind·CSS 변수 기반이다.
세 제품을 한 플랫폼에서 띄우려면 **플랫폼 공통 영역**(제품 식별·솔루션 전환·계정)과
**제품별 작업 영역**(지도 기능·프로젝트 계층·결과·보고서)을 분리해 설계한다.
현재 `navigation.html`은 K-AQUAS·D-ROAD 작업 셸 1차 견본이지 통합 플랫폼 셸의
확정안이 아니다. D-FIND를 K-AQUAS나 D-ROAD의 배치로 복제하지 않는다. 새 전역 바를
별도로 쌓으면 지도가 작아지므로 기존 상단 맥락과 합치는 후보부터 검토한다.

제품 API, 권한 정책, 고대비 테마 구현, D-FIND 브랜드 토큰·시각 견본, 실제 200%
브라우저 확대와 스크린리더, 소유자 최종 승인은 아직 끝나지 않았다. 가상 업무
견본을 현행 제품 동작으로 표현하지 않는다. D-ROAD 일괄 삭제는 미사용 API 근거의
조건부 후보이고 파일별 부분 성공·수치 진행률은 제품에서 확인된 동작이 아니다.
로고 분석, 대표 화면 제작, 제품 코드 적용, 페이지 꾸미기는 현재 범위에서 제외한다.

## 다음 작업

1. 세 제품을 수용하는 플랫폼 공통 영역과 제품별 지도·관리 작업 영역의 경계를
   `navigation.html`의 시각 견본으로 검토한다. D-FIND는 실제 브라우저 확인 전까지
   정적 소스 근거의 후보로 표시한다. 지도형 패널 폭·관리형 헤더·메뉴 치수를 최종
   Core 규칙으로 확정하지 않는다.
2. 실제 브라우저 200% 확대, 나머지 키보드 경로·스크린리더를 검증하고 발견된
   디자인 결함만 고친다. 검증하지 않은 항목은 [현재 상태](STATUS.md)에 그대로 둔다.
3. 소유자에게 Core 디자인을 보고해 최종 의견을 받는다. 제품 API·실제 적용과
   D-FIND 브랜드 토큰·전용 컴포넌트 설계는 별도 후속 단계다.

## 변경 절차

1. 기존 디자인 시스템 파일을 고치기 전에 목적·대상 파일·영향·되돌리는 방법을
   사용자에게 알린다. 문서·견본 수정은 알린 뒤 진행한다. 새 파운데이션 값·KRDS 예외·
   컴포넌트 추가/삭제는 소유자 결정을 따른다. 이미 요청한 범위의 구현은 재승인을
   받지 않는다.
2. 제품 근거는 `context/`, Core 결정은 `docs/`에 분리한다. 같은 문구를 여러 문서에
   반복하지 말고 기준 문서를 연결한다.
3. 토큰은 `tokens/source.json`에서 고친 후 `npm run tokens:build`를 실행한다.
   `tokens.css`를 직접 수정하지 않는다.
4. 견본·사용 기준·이 문서·`docs/STATUS.md`를 맞춘다. `npm run check` →
   `git diff --check` → 브라우저 검증 → 커밋·`main` 푸시 → GitHub Pages 확인 순서로
   마무리한다. 확인하지 못한 것을 완료로 쓰지 않는다.

현재 Pages는 공개 사이트다. 민감한 업무 데이터와 내부 구현 자료를 올리지 않는다.
사내 전용 운영 방식은 제품 적용 때 결정한다.
