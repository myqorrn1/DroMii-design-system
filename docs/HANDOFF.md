## 현재 목표

K-AQUAS와 D-ROAD의 공통점을 바탕으로 **공공기관 실무자가 사용하는 DroMii Core**를
정의한다. 공공서비스의 명확성·접근성·오류 복구에 KRDS를 기본 설계 기준으로 적용하되,
제품 로고·기준색과
수질·도로 업무의 차이를 유지한다. 공식 정부 누리집이라는 근거는 아직 없다.

현재 결과물은 HTML·CSS 시각 견본과 Markdown 사용 기준이다. **디자인 확정본도,
제품 코드에 바로 적용되는 React 패키지도 아니다.** 대표 화면은 사용자가 원하지 않아
제거했으며 Core가 확정될 때까지 다시 만들지 않는다. 제품 코드 적용도 이후 단계다.

## 이번 방향 조정

- 유지: 코드 중심 관리, 역할 토큰, 제품별 로고와 기준색, 헤더·메뉴 공통 구조,
  라벨·오류·상태·키보드 기준.
- 변경: 폼 기본형을 2열에서 1열로 바꾸고, 연관된 날짜처럼 짧은 필드만 2열 예외로 둔다.
  앱 셸 견본에는 본문 건너뛰기를 추가한다. 일괄 작업이 없는 사용자 표에서는 선택 열을
  없애고, 날짜·행 동작을 명확하게 한다.
- 검증 전: D-ROAD 다크 기본값, 표·지도·업로드의 높은 정보 밀도, 기관별 납품 규격,
  공식 정부 표식의 적용 여부.

판단 근거와 적용 범위는 [`공공업무 방향`](PUBLIC_SECTOR_DIRECTION.md),
완료·미완료 목록은 [`현재 상태`](STATUS.md)에 기록한다. 프런트 실측은
[`운영 소스 확인`](../context/05-live-frontends-2026-09-23.md)을 따른다.

## 다음 작업 순서

1. 1열 폼과 앱 셸의 200% 확대·세부 키보드 검증을 완료한다. 폼·메뉴·표의
   1024·1200·1440·1920px에서 가로 넘침이 없고, 본문 건너뛰기는 Tab·Enter로
   표시와 실제 초점 이동을 확인했다.
2. [`데이터 테이블`](DATA_TABLE.md)의 실제 선택형 목록과 검색·필터·긴 표,
   권한 제한·위험 동작의 공통 규칙을 설계한다.
3. 업로드와 지도 업무 패턴을 설계하고 K-AQUAS·D-ROAD에서 교차 검증한다.
4. Core가 확정된 뒤 React 공용 패키지와 신규 화면 적용을 시작한다.

## 모든 작업에서 지킬 절차

1. 기존 GitHub 디자인 시스템을 **수정하기 전에** 사용자에게 목적, 대상 파일,
   핵심 변경, 배포 및 제품 영향, 되돌리는 방법을 알린다.
2. `context/`에서 제품 코드의 사실과 Core의 새 결정을 분리한다. KRDS 기준과
   전문 업무 예외를 각각 기록하고, 실제 계약상 의무라고 추정하지 않는다.
3. 토큰은 `tokens/source.json`을 수정하고 `npm run tokens:build`로 생성한다.
   HTML 견본의 공용 스타일은 `components/base.css`에 둔다.
4. 변경마다 HTML 견본과 사용 기준 MD, 이 문서의 현재 상태·다음 작업,
   `docs/STATUS.md`, 필요 시 README 변경 이력을 함께 갱신한다.
5. `npm run check`, `git diff --check`, 브라우저 시각·키보드 검증을 수행한다.
   성공한 작업만 `main`에 반영하고 GitHub Pages 배포까지 확인한다.

로고의 의미·형태 분석은 제외한다. 대표 화면을 임의로 되살리지 않는다. 제품에 직접
적용하지 않는다. 이 조건이 바뀌면 사용자 지시를 우선하고 문서에도 변경을 남긴다.

현재 견본은 공개 GitHub Pages에 배포되고 있으나 사용자가 원하는 최종 공개 범위는
사내 전용이다. 민감한 업무 데이터나 내부 구현 자료를 Pages에 싣지 말고, 최종 운영
단계에서 사내 접근 통제 방식으로 옮길지 결정한다.
