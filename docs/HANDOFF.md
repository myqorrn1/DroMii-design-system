## 목표와 판단 순서

K-AQUAS와 D-ROAD의 기존 디자인을 **추출·리팩토링**해 드로미 솔루션이 공유할
DroMii Core를 만든다. 제품의 기준색·제공 로고·메뉴 구조·익숙한 업무 흐름을 먼저
보존하고 접근성, 불일치, 임시방편, 라이브러리 기본값을 고친다.

1. 제품 코드에 실제 근거가 있는가?
2. 두 제품에 공통인가, 또는 Core로 올릴 가치가 있는가?
3. KRDS와 접근성 기준으로 문제 없는가? 다르게 가면 근거를 예외 목록에 남겼는가?

KRDS는 기반이 아니라 점검 기준이다. 구체적인 채택·제외 범위와 공식성에 관한 경계는
[`KRDS 채택 범위와 예외`](PUBLIC_SECTOR_DIRECTION.md) 한 곳에서 관리한다.

## 현재 위치

- **단계 0 완료:** 선택형 로그 표의 가상 검색·선택·삭제 확인 견본, 320px·512px 유효
  화면에서 앱 셸 재배치와 표 스크롤, 사용 문서를 커밋 `84b8b26`으로 배포했다.
- **단계 1 완료:** 사용자 정정에 맞춰 방향 문서, 적용 순서, 진행 상태를 다시 정리했다.
  제품 값·토큰 값과 기존 서비스는 이번 단계에서 바꾸지 않았다.
- **단계 2 완료:** 운영 D-ROAD `dromii_v5_react/src` 전체와 로컬 K-AQUAS 루트 `src`
  를 읽기 전용으로 감사했다. [제품 소스 재감사](../context/06-product-audit-2026-09-23.md)
  에 값·구조·MUI·접근성 문제, 소스와 운영 번들 관계의 한계를 기록했다.
  `context/01-as-is.md`의 과거 수치와 경로 오류도 표시·수정했다.
- **단계 3 완료:** 제품·Core·KRDS 사이에 차이가 큰 본문 크기·밀도, D-ROAD 다크
  기본값·고대비 자리, 좁은 패널 컨트롤 높이를 대화로 보고했고 소유자가 추천안 세 가지를
  승인했다. [`KRDS 예외 목록`](PUBLIC_SECTOR_DIRECTION.md)에 실제 결정과 근거를 기록했다.
- **단계 4 구현·검토 중:** `tokens/source.json`을 `reference / semantic / component`로
  나누고 `brand / scheme / density` 축을 분리했다. K-AQUAS 파랑·라이트와 D-ROAD
  보라·다크 기본값을 보존했다. default 본문 16px, 제한된 compact 본문 14px,
  매직 넘버 대비 검사를 적용했다. 두 제품의 이전·기본·compact 표현은
  [`파운데이션 전후 비교`](../foundations/comparison.html)에서 확인한다.
  이 구현과 비교 견본은 단계 4 소유자 검토 대상이며, 제품 코드는 변경하지 않았다.
  `npm run check`는 토큰 경로 300개·고유 CSS 변수 211개·HTML 19개와 네 가지
  브랜드×명도 조합의 지정된 대비를 통과했다. 이전 토큰 스냅샷과 비교해 두 제품의
  기본 조합 색상 역할값은 각각 66개 모두 같다. `git diff --check`도 통과했다.
  로컬 `file://` 브라우저 접근은 이전 단계에서 URL 보안 정책으로 차단됐다. 우회하지
  않았으므로 이번 비교 견본의 실제 시각·확대 검증은 아직 완료하지 못했다.

## 이후 단계와 중단 지점

1. **단계 4 — 검토 지점:** 승인된 값으로 만든 토큰·견본의 전후 비교와 검사 결과를
   보고한 뒤 **소유자 승인을 기다린다**. 브라우저 시각 검증이 불가능한 경우 범위를
   숨기지 않고 남긴다.
2. **단계 5 — 업무 패턴:** 단계 4 승인 후 표·검색의 서버 상태, 위험 동작,
   업로드, 지도 순으로 만든다.
   대표 화면은 계속 보류한다. 제품 적용은 [`적용 가이드`](APPLICATION.md)에만
   전략을 기록하고 이번 범위에서 구현하지 않는다.

전체 순서와 완료 조건은 [`로드맵`](ROADMAP.md), 실제 완료·미완료는
[`현재 상태`](STATUS.md)를 따른다.

## 변경 절차

1. 기존 저장소 수정 전에 사용자에게 목적·대상 파일·배포 및 제품 영향·되돌리는 방법을
   알린다. 문서 정리와 견본 수정은 알린 뒤 진행한다. 파운데이션 값 변경, 새로운 KRDS
   예외 결정, 컴포넌트 추가·삭제는 명시적 승인을 받는다. 이미 사용자가 특정 단계에서
   지시한 변경은 그 지시를 따른다.
2. 제품 코드의 사실은 `context/`, Core 결정은 `docs/`에 분리한다. 과거 Vite 기록을
   운영 D-ROAD 근거로 재사용하지 않는다. 제품 코드·서버·운영 환경은 읽기만 한다.
3. 토큰 변경은 `tokens/source.json` → `npm run tokens:build` 순서로 하고 생성 파일
   `tokens.css`는 직접 수정하지 않는다. 공용 CSS는 `components/base.css`에 둔다.
4. 변경마다 견본·사용 기준·이 문서·`docs/STATUS.md`를 맞춘다. 같은 제한 문구를
   여러 문서에 복사하지 말고 기준 문서로 연결한다.
5. `npm run check` → `git diff --check` → 브라우저 확인 → 커밋·`main` 푸시 →
   GitHub Pages 확인 순으로 끝낸다. 검사하지 않은 것을 완료로 쓰지 않는다.

로고 분석, 대표 화면 제작, 제품 코드 적용은 현재 범위가 아니다. 현재 공개 Pages에는
민감한 업무 데이터와 내부 구현 자료를 올리지 않는다. 사내 전용 운영 방식은 제품 적용
단계에서 별도로 정한다.
